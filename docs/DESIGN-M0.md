# 消息服务设计（M0）

> 一期核心。**把消息层从第三方推送服务换成我们自己的。**

---

## 为什么换

现方案跑在第三方公共推送服务上，它**能推通知，但不是会议室**：

| | 推送服务 | 群聊需要 |
|---|---|---|
| 消息留存 | 服务默认 **12 小时清空** | 永久，能翻历史 |
| 身份 | 猜对地址就能进 | 有成员、有权限 |
| 会话 | 无状态，发完就完 | 有历史、有上下文 |

**结论**：做小工具够用，做群聊地基不对。

---

## 技术选型

| 项 | 选择 | 为什么 |
|---|---|---|
| 语言 | **Go** | 编译成**单文件二进制** —— 一行安装、跨平台交叉编译、无运行时依赖 |
| 存储 | **SQLite** | 单文件、零运维、自带事务。群聊这个量级绰绰有余 |
| 浏览器通道 | **WebSocket** | 实时、能显示在线状态 |
| 设备通道 | **HTTP** | ESP32 只会 HTTP，必须保留 |
| 部署 | **单个可执行文件** | 不依赖 Node/Python 运行时，`curl \| sh` 才成立 |

**为什么不选 Node**：要拖一整套运行时，桌面端"一条命令装好"就不成立了。
**为什么不选 Rust**：更安全，但开发慢。我们要的是快速推进，Go 够用。

## 数据结构

```
groups    群     id, name, owner_token, created_at
members   成员   id, group_id, name, kind(human/agent/device), token, created_at
messages  消息   id, group_id, sender_id, body, created_at
```

**要点**：
- `members.token` —— **每个成员一把钥匙**，不是全群共用一把
- `messages` 只增不改，**永不删除**（这是和推送服务的根本区别）

## 接口

### 收发消息

```
POST /api/{group}/messages          # 发消息
     Authorization: Bearer <token>
     {"body": "内容"}

GET  /api/{group}/messages?since=<id>   # 拉消息（设备轮询用）
     Authorization: Bearer <token>

WS   /api/{group}/ws                    # 实时订阅（浏览器用）
     Authorization: Bearer <token>
```

### 管理

```
POST /api/groups              建群 → 返回群 ID 和管理员令牌
POST /api/{group}/members     加成员 → 返回该成员的令牌
GET  /api/{group}/members     成员列表
```

**设计原则**：**一条 HTTP 就是一条消息** —— 不带额外的概念包袱，
任何语言三行代码就能接入（这是设计信条一）。

---

## 安全要求

1. **每个成员独立令牌** —— 泄露一把只影响一个人，可单独撤销
2. **无令牌的请求一律拒绝** —— 默认关闭，不是默认开放
3. 令牌**只存哈希**，数据库泄露也不至于直接能用
4. 管理接口（建群/加成员）需要管理员令牌

## 验收标准

做完逐条**实测**，不靠"看着对"：

| # | 验收项 | 怎么测 |
|---|---|---|
| 1 | **重启不丢消息** | 发 3 条 → 重启服务 → 全在 |
| 2 | 浏览器实时收到 | 两个窗口，一个发一个收 |
| 3 | **curl 也能收发** | `curl` 发、`curl` 拉，都通 |
| 4 | **无令牌被拒** | 不带令牌 → 401；带错令牌 → 401 |
| 5 | **一条命令起** | 新机器：`./tigertally serve` 就能跑 |

**外加**：把验尸结果写进 `docs/M0-RESULT.md`，包含**实际命令和实际输出**。
